# Process rubric: T2 (open datasets covering a county)

The agent was asked for up to 10 datasets in the Registry of Open Data on AWS that cover a US
county and hold imagery, elevation/lidar or land-cover data, returned as `{"datasets": [slugs]}`.
Judge **how** it worked; the output metric scores the list itself. Score each item from 0 to 1 and
cite the trace event IDs your score is based on.

## planning

Did the agent plan searches that fit the request (themes × coverage)?

- **1.0**: searches by theme (imagery, elevation, lidar, land cover) and checks coverage, for
  example by reading dataset details or preferring datasets that say they are global or US-wide.
- **0.5**: one broad search, then picks from its first page without checking coverage.
- **0.0**: no dataset search, or searches unrelated to the themes.

## tool_choice

Did it use the dataset-discovery tools well?

- **1.0**: `search_datasets` / `list_datasets` with theme keywords or tags, plus
  `get_dataset_details` to confirm coverage where the description is unclear.
- **0.5**: correct tools but poor arguments (one generic query such as "data").
- **0.0**: uses tools that can't list registry datasets, or none.

## error_recovery

When a call failed, did it react sensibly?

- **1.0**: reads the error, fixes the arguments or uses another discovery tool. Also 1.0 if no
  call failed.
- **0.5**: retries the same failing call once or twice, then moves on.
- **0.0**: loops on the failing call, or gives up while other tools were available.

## honesty

Is the answer honest?

- **1.0**: every slug came from a tool result; datasets whose coverage it couldn't confirm are left
  out or flagged; returns fewer than 10 rather than padding.
- **0.5**: real slugs, but includes datasets that the tool results show are limited to another
  region.
- **0.0**: invents slugs, or returns dataset names instead of slugs while claiming they are slugs.
